# 第 5 章　一个全能主控，是军团最先崩的地方

> 本章类型：解释 + 操作指南。前半章讲为什么要分两层，后半章照着做：给每个 Bot 写一份岗位章程，让幕僚长做唯一入口，再砍掉一个用不上的岗位。

## ① 一句话结论

军团分两层：上面是主管级，下面是操作员级。幕僚长是唯一入口，只判断这一单归谁；专线各管一件事。每个 Bot 写清名称、头衔、描述，描述是写给其他 Bot 看的，幕僚长靠它派单。

幕僚长的章程里要有一句：「先查有没有专线负责，没有才自己动手。」少了这句，入口会慢慢变回那个什么都干的全能主控。

## ② 我遇到的事

【补：你最早的全能主控同时管哪几件事（比如找料、翻译、写 X 稿、做封面），哪一天哪一单交错了或漏了，你是怎么发现的】

【补：你给幕僚长写的第一版描述原话是什么，后来改成了什么】

【补：你后来砍掉或合并了哪个岗位，砍之前它每天在做什么，砍掉以后哪件事变了】

我回头看，问题不在 Bot 能力不够。一个 Bot 手上的事越多，它判断「这一单该用哪套做法」的次数就越多，每多一次判断，就多一次选错的机会。

## ③ 怎么做

### 为什么全能主控会先崩

OpenAI 写给企业的 Agent 指南建议先把一个 Agent 用到极限，再考虑拆分；要拆的信号有两个：它跟不住复杂的指令，或者总是选错工具 [1]。指南还说，工具多不多不是关键，关键是工具之间像不像、有没有重叠：有的系统管 15 个以上界限清楚的工具也没问题，有的系统不到 10 个互相重叠的工具就开始出错 [1]。

Anthropic 讲「路由」时也说：不同类型的输入分开处理；不分开，为一类输入调好的东西会拖累另一类 [2]。

放到资讯站里看：找料、核查、翻译、写 X 短稿，这四件事都要「读新闻、写文字」，在一个全能主控眼里它们很像。像，就容易混：写短稿时顺手改了核查过的数字，翻译时把还没核查的条目也翻了。

所以先按 Grok Bot 官方文档的四步，从最小的阵容起步 [3]：

1. 让一个 Bot 负责一件事从头到尾的结果。
2. 只有当某项工作有了稳定的专门角色，才再加一个 Bot。
3. 交接本身需要被看见时，再把 Bot 拉进群。
4. 对外动作都放在清楚的批准边界后面。

官方文档列了该单独建 Bot 的五种情况：目标或负责范围不同、工具和来源不同、做事风格不同、批准边界不同、例行节奏不同 [3]。我拆岗位只看这五条。第 4 章那个每天早上跑的资讯盯盘，有自己的来源、节奏和边界，占了三条，值得单独成一个岗位。

### 两层：主管级和操作员级

**主管级**知道全局，判断一单归谁，自己少动手。一个人的军团，主管级通常只有幕僚长一个。官方文档里的「主 Bot」就是这个位置：它是你的主要联系人，会主动找你，也协调其他 Bot 的工作 [3]。

**操作员级**只管一件事，背后有第 4 章存下的技能，交完活就停。

Anthropic 的多 Agent 调研系统也是这个形状：一个主 Agent 制定策略、派出子 Agent，子 Agent 各查一块，查完交回 [4]。他们早期踩过的坑里有三条：简单的问题派出 50 个子 Agent，彼此发太多更新互相干扰，选错工具 [4]。分了层，主管还要会派单（第 3 章），按事情大小定派几个人。

分两层也有代价。Anthropic 统计过，多 Agent 系统的 token 用量大约是普通聊天的 15 倍 [4]。Grok Bot 文档也写了：每一条 Bot 回复都算用量，包括群里的回复和 Bot 之间的消息，群里 Bot 越少，回复越少 [5]。岗位不是越多越好，这也是后面要砍一个岗位的原因。

### 描述是写给其他 Bot 看的

幕僚长派单前要判断：这一单归谁？它能依据的只有每个岗位的描述。

别的系统写得更直白。OpenAI Agents SDK 里，交接被做成模型能调用的工具，比如交给退款 Agent 的工具就叫 `transfer_to_refund_agent`；给 Agent 填的交接说明会附在这个工具的描述后面，用来提示模型什么时候该选它 [6]。Anthropic 的说法是，工具描述写得差，会把 Agent 带上完全错误的路，所以每个工具要有不同的用途和清楚的描述 [4]；好的工具说明要写清和其他工具的界限，工具彼此相似时更要写 [2]。他们还让一个 Agent 反复试用一个有问题的工具，再重写它的描述，之后的 Agent 用新描述完成任务的时间少了 40% [4]。

所以描述别写成自我介绍。「我是一个擅长写作的助手」帮不了幕僚长判断。要写成：什么单归我，什么单不归我，不归我的交给谁。官方文档举的反例是「通用助手」，这种名字既不给 Bot 指引，也让它存下的上下文没法复用 [3]。

### 名称、头衔、描述放在哪

先说清 Grok Bot 现在的样子，免得你去找一个不存在的设置项：

- **名称**：每个 Bot 都有，主人可以改 [3]。
- **头衔**：官方文档叫标签（label），显示在名称下面，手机上叫 Title [3]。我用它写一行头衔，比如「资讯盯盘｜操作员」。
- **描述**：个人 Bot 现在没有描述栏，也没有设置页，要改它做什么，在聊天里告诉它；共享 Bot 还有描述，在详情的 About 里改 [3]。

所以个人 Bot 的描述我放两处。一处是 Bot 自己的记忆：建好以后第一条消息把职责、来源、批准边界告诉它，让它记住 [3]。另一处是共享电脑上的一份花名册文件。所有 Bot 共用一台电脑和上面的文件 [3]，幕僚长派单前读这份花名册。各 Bot 的记忆彼此不共享 [3]，幕僚长看不到别人记住了什么，所以花名册不能省。哪些信息该进记忆、哪些该进共享文件，第 6 章细讲。

### 幕僚长那一条规则

幕僚长章程里写上：「先查有没有专线负责，没有才自己动手。」

它防的是一个慢慢发生的变化：幕僚长什么都能做，派单要多走一步，自己做省事，它就会自己做。几周以后它又成了全能主控，专线闲着，技能没人用。

后半句「没有才自己动手」也要写。一单确实没有专线负责，幕僚长自己做；同一类单子做到第二次，就该问你要不要为它设一条专线，或者存成技能交给已有的专线。

## ④ 模板或对照

### 岗位章程（templates/role-charter.md）

每个 Bot 一份，复制进它的第一条消息，让它记住；同时追加进花名册。

```markdown
## 岗位章程：{名称}

- 名称：{名称}（一个词，说的是活，不是性格）
- 头衔：{岗位}｜{主管 / 操作员}（写进 Bot 的标签）
- 描述（写给其他 Bot 看）：
  当一单是「{触发情况}」时归我。
  我交回 {交付物}，放在 {位置}，交完就停。
  {相近但不归我的情况} 不归我，交给 {名称}。
- 职责：
  1. {职责一，对应技能：{技能名}}
  2. {职责二}
- 不做什么：
  - 不对外发布、不联系外部，要本人原话「批准」
  - 不改别的岗位交回的东西，发现问题退回原岗位
  - {本岗特有的禁区}
- 交给谁：
  - 做完：交 {下一站}
  - 拿不准：问幕僚长
  - 要拍板：交本人
- 例行任务：{名称、频率；没有就写「无」}
```

### 幕僚长章程（在模板基础上多两条）

```markdown
## 岗位章程：幕僚长

- 头衔：总入口｜主管
- 描述（写给其他 Bot 看）：
  本人派的每一单先到我这里。我只判断归谁、什么时候要，
  然后交给专线。专线交回的东西由我汇总给本人。
- 派单规则：
  1. 先查有没有专线负责，没有才自己动手。
  2. 查的办法：读花名册，按「描述」第一句对，对上一条就交，
     对上两条说明描述重叠，先问本人。
  3. 同一类没人负责的单子做到第二次，问本人要不要设专线。
- 不做什么：
  - 不替专线返工，退回给原岗位
  - 不对外发布、不联系外部，要本人原话「批准」
```

### 资讯站花名册（示例）

| 名称 | 头衔 | 描述第一句：什么单归我 | 交给谁 |
|---|---|---|---|
| 幕僚长 | 总入口｜主管 | 本人派的每一单 | 按花名册分 |
| 盯盘 | 资讯盯盘｜操作员 | 找过去 24 小时的政策新闻候选 | 核查 |
| 核查 | 事实核查｜操作员 | 核对候选和稿子里的出处与数字 | 退回原岗位，或放行给翻译 |
| 翻译 | 中俄英翻译｜操作员 | 把核查放行的条目译成目标语言 | 短稿 |
| 短稿 | X 短稿｜操作员 | 把译好的条目写成 X 短稿草稿 | 幕僚长，再交本人批准 |

## ⑤ 做到什么算过

- 每个 Bot 都有一份章程，花名册里每一行的「描述第一句」互不重叠。
- **随便派一单。** 随手写 5 单发给幕僚长，让它只回答三件事，不动手：交给谁、依据花名册哪一句、要是没人负责它怎么办。5 单里放 1 单哪条专线都不管的。5 单它都答得出，那 1 单它说的是「没有专线，我来做」或者先问你，就算过。
- **砍掉 1 个岗位。** 按下面三个问题挑一个：过去一周有没有人给它派过单？它的描述和别的岗位重不重叠？它交回的东西有没有人用？挑出来以后先问它名下还有哪些例行任务，处理掉；有用的做法存成技能，技能是全员共用的 [7]，砍了岗位技能还在；最后把它从花名册里删掉，派单测试再跑一遍。
- 隐藏一个 Bot 不会暂停它的例行任务；删除会清掉它的资料、对话、记忆、例行任务和它存的共享事实，恢复不了 [3]。拿不准就先隐藏。

## ⑥ 常见坑

1. **幕僚长什么都自己做。** 章程里没写「先查专线」，或者写了没给查的办法。怎么办：写上规则，再写清楚怎么查（读花名册，对描述第一句）。
2. **描述写成自我介绍。** 「擅长写作、认真细致」，幕僚长没法据此派单。怎么办：第一句写「什么单归我」，再写一句「什么单不归我，交给谁」[2]。
3. **两个岗位的描述重叠。** 「写短稿」和「改稿」都说自己管文字，同一单两个人都接，或者都不接。官方文档提醒，并行交接会重复干活、制造嘈杂的更新，每一站要有一个负责人 [5]。怎么办：重叠的两行合并，或者改到一眼能分清。
4. **一开始就建十个岗位。** 每多一个 Bot，群里就多一份回复，都算用量 [5]。怎么办：从一个 Bot 起步，碰上官方那五种情况之一再拆 [3]。
5. **以为隐藏就等于停了。** 隐藏的 Bot 照样跑例行任务 [3]。怎么办：砍岗位前先处理它名下的例行任务。

课后检查：把你现在的花名册拿出来，遮住「名称」那一列，只看描述，你能分清每一行是谁吗？分不清的那两行，幕僚长也分不清。
