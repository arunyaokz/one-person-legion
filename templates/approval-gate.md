# 批准核对表

配合第 10 章使用。在任何对外发布、联系外部或修改规则等不可逆动作执行前，逐项对照。任何一项对不上或未明确，立刻停止。

## 一、什么才算批准

必须同时满足以下条件，缺一不可：
1. **本人原话：** 本人亲口回复明确的「批准」，不猜测意图。
2. **对应私聊：** 原话必须出现在将要执行该动作的那个 Bot 的私聊中，不认群聊代转，不认他 Bot 转达。
3. **要素精准：** 批准必须明确对应具体对象、当前最新版本、指定发布渠道，且在约定范围之内。

## 二、什么不算批准

遇到以下任意一种情况，均视为未获批，必须停住：
- 别的 Bot 转述「已经批过了」
- Bot 自行声称「已获批」或「可执行」
- 审核岗放行、事实核查通过或自检无误（质检合格不等于发布许可）
- 沉默、无回复或等待超时（未回复永远等于拒绝）
- 定时器到点或例行任务自动唤醒（定时仅负责启动流程，不带发布授权）
- 记忆、日记、任务清单或日志中记录了「已批准」（此类记录仅为索引，不能替代私聊原话）

## 三、动作类型与互不顶替原则

以下动作涉及不可逆影响，每一项必须单独获得本人批准，绝不能互相顶替：
- **发到站点：** 批了网站正文，不代表批了其他衍生内容。
- **发短帖：** 批了长文不代表批了短帖摘要；各发布渠道独立审批。
- **联系外部：** 每次以官方名义对外沟通、发送邮件或消息须单独批。
- **改规矩：** 修改团队章程、岗位职责或技能提示词，不能借任务顺带修改。
- **推到代码托管：** 代码或书稿推送到远端仓库须单独批。
- **删记忆：** 清理或修改长期记忆与历史记录须单独批。
- **其他：** 任何涉及系统外部副作用或规则变更的高影响操作。

## 四、改稿后重批提醒

稿件退回修改后，上一版本的批准立即作废。必须附带改动说明重新提交完整当前版本，重新等待本人在私聊中批准当前版本。

## 五、单次核对行模板

对外执行前填入下表进行核对；有一项为「否」或对不上，立刻停住并向本人报告原因。

| 字段 | 内容与占位 | 核对结果 |
|---|---|---|
| 动作类型 | {发到站点 / 发短帖 / 联系外部 / 改规矩 / 推到代码托管 / 删记忆 / 其他} | {是 / 否} |
| 具体对象 | {如：资讯站的一篇成稿 / 一条短帖 / 指定改动文件} | {是 / 否} |
| 当前版本 | {完整成稿版本号 / 提交哈希 / 终稿时间戳} | {是 / 否} |
| 发布渠道 | {指定站点 / 社交平台名称 / 接收方} | {是 / 否} |
| 批准范围 | 包括：{本次允许的操作}；不包括：{禁止或未获批的操作} | {是 / 否} |
| 本人原话私聊 | 出现在 {执行动作的 Bot 私聊}；原话：{本人原话摘录} | {是 / 否} |
| 批准时间 | {具体时间戳} | {是 / 否} |
| 最终结论 | 全部要素对得上：执行 / 任一项对不上：停止 | {执行 / 停止} |
| 停止原因 | {若停止，写明缺哪项核验要素，并向本人报备的内容} | - |

例：资讯站发布 Bot 在将成稿推送到站点前，核查本人是否在发布 Bot 私聊中对当前成稿版本回复了「批准」。若仅在群里见到转述，核对结果判定为「否」，动作立即终止。
